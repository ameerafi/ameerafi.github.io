01 / Approach

How I work, when nobody's watching

Weigh the options before committing

On the streaming rebuild I evaluated several replication and streaming designs, took opinions from the teams who'd have to live with it, and proposed both a short-term and a long-term answer. The fast decision is rarely the cheap one.

Understand the rule before you automate it

Most of these systems encode finance logic, not engineering logic. I sit with the operations team until I can state the business rule precisely, then automate. Automating a rule you half-understand just produces wrong answers faster.

Automate it, then hand it back

Every automation I've shipped came with an SOP and a handover, so the team that owns the process can run it without me. Retaining the dependency looks like job security and is actually a bottleneck.

Make failures loud, and write them down

A parser once silently dropped transaction types it didn't recognise, and the balance quietly stopped matching. I fixed it, then documented the failure mode so the next person finds it in an afternoon instead of a fortnight.

Four things worth explaining

All four at Amazon Pay, on India's regulated payment accounts. Internal system names are generalised; figures are stated relative rather than absolute.

Amazon Pay · Data Engineer II · 2023–2024

Cut reporting latency from 36 hours to 30 minutes

Downstream teams were reporting on data that was up to a day and a half old. The batch extract was the bottleneck, and no amount of tuning was going to close a 36-hour gap — it needed a different shape.

36h → 30mReporting SLA
~99%Latency reduction
8 moLive with zero defects
0Production incidents

Problem

Order transaction data reached downstream consumers on a 36 to 40 hour SLA. Reporting was therefore always describing a state of the world that had already moved. The extract ran on a schedule, so latency was structural — a faster machine would not have helped.

Approach

I gathered the constraints from every team that consumed the data, evaluated several replication and streaming designs against them, and put forward two options: something we could ship within the quarter, and the architecture we should converge on. Batch became event-driven ingestion.

Architecture

  1. 1
    Stream at the source

    Database change streams pushed to object storage in the source account, near real time, so nothing sat waiting for a schedule.

  2. 2
    Replicate across accounts

    Cross-account, per-region replication of the encrypted payload, so the consuming platform never reached into the producing one.

  3. 3
    Transform on arrival

    An upload event triggered the transform rather than a timer — the pipeline moved when data moved, not when the clock did.

  4. 4
    Alarm on absence

    Failure alarms raised a ticket automatically, so a silent stall surfaced as an alert rather than as a question from a confused analyst.

What changed

Reporting SLA went from 36–40 hours to 30 minutes, a reduction of roughly 99%. More telling than the latency number: the system ran in production for eight months with zero defects. My manager put both figures in writing in my promotion document, which is the version I quote — I would rather use a number somebody else signed.

Amazon Pay · Data Engineer · 2022–2023 · Merchant integration metrics

Near real-time metrics from a table the warehouse couldn't reach

The second metric in the merchant integration funnel was missing entirely. The data existed, in a NoSQL table owned by another team, in another account, with restricted fields mixed in. Nobody had a route from there to the warehouse.

15–30mData availability SLA
100%Data accuracy
0Job failures
PIIStripped in flight

Problem

Key generation timestamps sat in a NoSQL table owned by another team. Cross-account, cross-region, encrypted, and carrying restricted personal data that could not be allowed into the analytics estate at all. The BI team had simply been reporting the funnel with a hole in it.

Approach

Treat the compliance constraint as the first design input rather than a later review gate. If restricted fields can never land in the warehouse, the exclusion has to happen in flight, before anything is written — which decides the architecture, not the other way round.

Architecture

  1. 1
    Stream and replicate

    Source team streamed table changes to object storage; I set up cross-account replication per region with a customer-managed encryption key held on the destination side.

  2. 2
    Transform on upload

    An upload event invoked a Python transform that dropped restricted fields, reshaped to the business specification, and wrote partitioned Parquet — so restricted data never reached durable analytics storage.

  3. 3
    Keep the catalogue current

    A crawler maintained partitions automatically, making each file queryable as soon as it landed rather than after the next catalogue run.

  4. 4
    Backfill separately

    History loaded as a one-time job, kept apart from the live path so a large backfill could never delay current data.

  5. 5
    Alert on failure

    Alarms raised a ticket, and a notification script told the actual end users — not just the on-call engineer — when something had not arrived.

What changed

The funnel metric existed for the first time, at a 15–30 minute SLA, with 100% data accuracy and zero job failures. The part I am most pleased with is the compliance design: restricted fields were excluded before anything durable was written, so there was never a cleanup problem to solve later. My manager's assessment singled out the simplified approach to handling regulated data in the lake.

Amazon Payments · Reconciliation · 2021–2022

Twenty million records reconciliation had been ignoring

During the pandemic, refunds started exceeding sales. That produced negative settlement amounts, which the processors could neither deposit nor draw back — so the files were simply skipped. The books had been quietly accumulating a gap for months.

20MRecords processed
100%Data accuracy
~2 daysManual effort removed
Multi-bnRupee backlog cleared

Problem

When refunds exceed sales the aggregate goes negative, and the processor holds the amount until sales catch up. Reconciliation processed the positive files and ignored the negative ones. The transactions were real, the money was real, and none of it was on the books — sitting instead in exception buckets that grew every month.

Approach

Validate before you load, never after. Twenty million financial records with no rollback story is not a place to discover a formatting assumption was wrong, so every batch went through a temporary table and an arithmetic check before anything touched a production table.

Architecture

  1. 1
    Collate in code

    Python reshaped the raw files into the three target table formats — the step that had previously been done by hand across eighteen settlement references.

  2. 2
    Prove it before loading

    Staged to a temporary table and checked that header amounts reconciled against aggregates. A mismatch stopped the load rather than being found downstream.

  3. 3
    Upload without hands

    Validated data and manifest files pushed to object storage via the SDK, with no manual step anywhere in the path.

  4. 4
    Close the contra buckets

    Loading the data was only half of it — the corresponding exceptions had to be knocked off. New query, revised business rules, stakeholder approval, then matching changes to the reports and dashboards.

What changed

Twenty million records loaded at 100% accuracy, removing around two days of manual work and clearing a multi-billion-rupee backlog from the remittance and bank mismatch buckets — the largest single reconciliation impact I delivered. The lesson that stuck: the load was the easy part. Getting the business rules right, and getting them approved, was the job.

Amazon Pay · Financial substantiation · 2021–2023

A five-day regulatory deadline, made one-click

Every month the regulated payment accounts had to be substantiated — proven to balance — within five working days. Validation meant around sixty reports and thirty dashboards, refreshed by hand, in order. When a variance appeared, finding the cause took four days out of the five.

~60 + 30Reports and dashboards orchestrated
5 daysTurnaround removed
4d → autoVariance root-cause analysis
Monthly → dailySubstantiation cadence

Problem

Sixty report jobs and thirty dashboards, each independent, none packaged into a workflow, all requiring someone to run them in the right order for the right date. And when the report did not balance, diagnosis meant checking run status across eighty scheduled jobs by hand — four days of the five-day window, spent looking rather than fixing.

Approach

Two separate problems wearing one coat. Running the reports was an orchestration problem. Diagnosing variance was a knowledge problem — the checks lived in people's heads. The second one had to be written down as rules before any of it could be automated.

Architecture

  1. 1
    Package the jobs

    Roughly sixty independent report jobs collapsed into three orchestrated workflows, each executable in one click for any given date.

  2. 2
    Automate the dashboards

    A script discovered all thirty dashboard dataset identifiers programmatically and refreshed them through the CLI, with credentials read from a managed material set rather than embedded.

  3. 3
    Encode the diagnosis

    I sat with the operations team until every variance check was a stated rule, then built validation templates that applied them automatically and populated the output.

  4. 4
    Watch the sources

    A dashboard monitoring unification status across every source table, so a missing upstream table was visible before it became a variance.

  5. 5
    Hand it over

    A checklist and an SOP so the finance operations team ran the whole thing themselves. It was not finished until it no longer needed me.

What changed

Validation went from a phased manual process to one click on demand — a day of effort and four days of turnaround removed from every cycle. Variance investigation dropped from roughly four days to automated. Because diagnosis was no longer expensive, substantiation moved from monthly to daily, which meant problems were caught days earlier instead of at month-end. The five-working-day regulatory deadline stopped being something to worry about.
