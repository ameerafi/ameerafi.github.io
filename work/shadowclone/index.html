Production-Risk-Free Performance Sandbox

Proving a 10× speedup against 4.45 billion rows, with production untouched

Optimizations measured on development data routinely fail under production volumes, and testing them in production risks data corruption and SLA breaches. ShadowClone removes the choice: it clones production inputs without copying them, runs the candidate job in an isolated sandbox, and emits an automated verdict on both data parity and cost.

The problem

Two bad options, and teams were picking one

The motivating incident: enabling Photon on a pipeline looked fine in development, then ran three times slower in production, breached downstream SLAs, and had to be reverted. Nothing about the dev test was wrong — the dataset was just too small to exhibit the skew, shuffle and file-scaling behaviour that actually decided the outcome.

That leaves two options, both bad. Test on dev data and ship on faith, discovering the truth during a production incident. Or test in production and accept the risk of corrupting real tables and breaching real SLAs.

Underneath both is a missing capability: there was no systematic way to demonstrate that a change left output data byte-identical while performance improved. Without that, every optimization is an argument rather than a measurement, and the cautious answer is always to leave it alone.

The blocker was never a lack of optimization ideas. It was the absence of a way to prove one safe before it touched anything that mattered.

The idea

Production-scale data, zero production exposure

Delta shallow clones make production-scale test data essentially free: a clone is metadata pointing at the same underlying files, so cloning a billion-row table costs no meaningful storage and takes seconds. That removes the usual reason dev datasets are small.

The rest is plumbing with one non-negotiable property: the sandboxed job must be structurally incapable of touching production. Not "configured not to" — incapable. A sandbox that depends on the operator being careful will eventually meet someone in a hurry at the end of a long day.

How it works

One command: discover, gate, clone, redirect, run, verify

Discover the lineage

Reads the catalog's own lineage tables to find every input the job actually touches, matching on job identity and unioning a 30-day lookback to catch inputs that only appear in monthly runs. Deliberately does not parse code — code lies, and lineage records what really happened. If lineage comes back empty it fails loudly rather than proceeding to clone nothing and report a meaningless pass.

Gate on identity, fail closed

Before anything runs, the sandbox verifies its own service principal's effective permissions — including grants inherited through group membership, which is where assumptions usually break — and pins the run identity. This is the load-bearing safety property: every later stage can be wrong and production is still unreachable, because the permission wall is upstream of the mistake.

Shallow-clone the inputs

Metadata-only Delta clones give production-scale data with no storage duplication. An optional clone-from-tag pins the clone to a known version, which separates code change from data drift — without it, a source table updating mid-test makes the parity result meaningless.

Redirect and run in isolation

Job parameters are patched dynamically at submission — no YAML edits, no forked job definitions to drift out of sync. Task types that cannot be safely redirected refuse to run rather than silently executing against production, which is the same fail-closed principle applied at the task level.

Prove parity

A bidirectional EXCEPT ALL between sandbox and baseline outputs. The bidirectionality matters: one direction catches dropped rows, the other catches added ones, and using multiset semantics rather than set semantics catches duplicates that a naive comparison would silently forgive. Schema drift surfaces here too.

Judge performance and cost separately

Runtime is measured on execution duration rather than wall-clock, so cluster startup noise does not contaminate the comparison. Cost attribution is a separate deferred subcommand, because billing data lands hours later — running it inline would confidently print $0.00 and be believed.

Engineering detail

Where the design earns its keep

Safety is structural, not behavioural

The identity boundary means a stray redirect hits a permission error, not a production table. The guarantee holds when the operator is wrong, which is the only kind of guarantee worth having in a tool people will use under time pressure.

One core change, 30+ pipelines

Rather than wiring each pipeline family individually, redirection hooks into the shared catalog resolver every pipeline already calls — a single backward-compatible change. Every family inherited the capability at once, across file-based, API-based, JDBC and streaming sources, with no per-pipeline code.

Lineage over static analysis

Parsing job code to find inputs is fragile the moment a table name is constructed at runtime. Reading actual lineage is both simpler and more correct, and the 30-day union catches the monthly job whose inputs a single run would never reveal.

Never print a misleading zero

The temptation is to show a cost figure immediately. Because billing data arrives with a lag, an inline number is wrong in a way that looks authoritative. Deferring it to its own step is less convenient and considerably more honest.

Multiset, not set, comparison

Set-based comparison treats a duplicated row as identical to a single one. For financial and reporting outputs that is exactly the class of bug you most need to catch, so parity is checked as a multiset in both directions.

Two engines, one core

A generic engine using catalog-swap redirection works for any parameterized job, including external customers. A platform-specific engine uses schema-prefix redirection for tighter integration. Both share the discovery, gating and verdict logic, so the safety properties are proved once.
