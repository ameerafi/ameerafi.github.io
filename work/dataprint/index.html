Algebraic Migration Verifier · Databricks Lakebridge

Proving two billion-row tables match without moving the data

Every enterprise migrating onto a lakehouse has to prove the target matches the source. The standard approach moves terabytes across the network to do row-by-row hash joins, so at real scale teams give up and sample. DataPrint compares compact algebraic fingerprints instead — and when they disagree, solves for the exact differing rows rather than searching for them.

The problem

Why migration validation quietly becomes guesswork at scale

After a migration you have the same logical dataset in two systems that disagree about almost everything physical — type widths, timestamp precision, null encoding, sort order, floating-point representation. Proving equality means comparing every row.

The conventional method hashes each row on both sides and joins the hashes. That forces a full extract of the source: a 74-million-row table takes about 506 seconds and pulls roughly 2.4 GB across the network. Scale that to a billion rows and it is hours to days per table; scale it to a hundred-table migration and it stops being viable at all.

So teams fall back to sampling ten percent and calling it confidence. But sampling cannot prove equality — it can only fail to disprove it. A migration sign-off built on a sample is an assertion, not a verification, and everyone in the room knows it.

The constraint worth attacking is not compute. It is the network. Any method that requires the rows themselves to move is bounded by egress, not by how fast you can hash.

The idea

Compare mathematics, not rows

If you hash each row to an integer, a table becomes a multiset of integers. Two multisets are equal if and only if their power sums agree — the count, the sum, the sum of squares, and so on. Those are single numbers, and critically they can be computed where the data already lives.

So instead of shipping rows to compare them, DataPrint asks each side for a handful of aggregates and compares those. On a clean migration the numbers match and the table is proven equal in one round trip.

The interesting part is what happens when they don't match. The differences between the power sums are not just a signal that something is wrong — they are a system of equations whose solution is the set of differing row hashes. You can recover exactly which rows differ by solving, rather than by hunting.

How it works

Four stages, short-circuiting as early as possible

Hash and partition

Every row is reduced to a 64-bit integer using a hash that is byte-identical across engines — the same row must produce the same integer in Redshift and in Spark, which means pinning type coercion and serialisation explicitly rather than trusting each engine's defaults. Hashes are then bucketed into roughly a million sub-buckets so a mismatch localises instead of contaminating the whole table.

Fingerprint each bucket at the source

Five algebraic signals per bucket: count, sum of hashes, sum of squares, and an independent second channel used purely for collision detection. Source-side aggregates are computed via JDBC pushdown, so the source database does the arithmetic and returns about 50 KB — no raw rows ever leave it. Target-side aggregates are computed natively in Spark.

Compare and short-circuit

The two aggregate sets are broadcast-joined. Matching buckets resolve immediately and are never examined again. On a healthy migration this is where almost the entire table resolves, which is why the common case is fast rather than merely faster.

Solve for the exact differences

For buckets that disagree, a single-pass algebraic solver recovers the differing row hashes from the power-sum deltas. One difference resolves directly and covers roughly 97% of real cases; two resolve through a quadratic; denser buckets or suspected collisions fall back to a surgical fetch of just that bucket. The output is the offending rows, not a red flag.

Engineering detail

The decisions that made it trustworthy rather than merely clever

Single-pass solver, not recursive bisection

The established tool in this space narrows down differences by repeatedly splitting ranges and re-querying — many round trips, each one paying network latency. Solving the power-sum equations recovers the same answer in one pass. This is the core departure and the reason the numbers move by an order of magnitude rather than a percentage.

Dual-channel collision detection

Any hash-based scheme can in principle be fooled by a collision. Running a second, independent aggregate channel makes a false match require a simultaneous collision in both — a combined probability around 2⁻¹²⁸. Cheap to compute, and it converts "almost certainly correct" into a bound you can state.

Zero false results by construction

The exact comparison is always the final arbiter: the algebra narrows the search space but never decides equality on its own. That ordering is what makes zero false positives and zero false negatives a structural property rather than a test outcome.

Cross-engine hash parity

The hardest part was not the mathematics. Getting two engines to agree on the byte representation of a timestamp, a boolean, and a float — before hashing — took more care than the solver did. Get this wrong and every row looks different.

Opt-in and fail-open

Shipped behind a configuration flag that defaults to off, falling back to the legacy path on any unexpected condition. Existing users are unaffected until they choose otherwise, which is the only responsible way to put a new correctness mechanism into a tool other people depend on.

Three latent bugs found on the way

Building cross-engine parity surfaced three pre-existing serialisation defects that had been silently corrupting every Redshift reconciliation: microsecond drift on timestamps, a crash on boolean handling, and precision loss on double and float. Fixed and centralised into a single type-transform lookup.

Reach

Contributed upstream into Lakebridge, Databricks' open-source migration tool, rather than kept as a one-engagement script. Redshift is production-ready; each additional source is roughly two to three days of work through a pluggable query-builder interface, because the algebra is engine-independent and only the SQL generation changes.

The library also ships standalone with 361 unit tests, seven validation notebooks, and YAML batch configuration for running a whole migration's worth of tables unattended.
